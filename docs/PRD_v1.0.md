## 一、产品定位

### 1.1 一句话定位

面向高校在校生的「二手书 + 全品类闲置」校内交易信息匹配平台，通过书单批量匹配核心差异化能力，降低学生教材采购成本与闲置物品流通门槛。

### 1.2 产品愿景

成为高校校园内最值得信赖的二手交易基础设施，让每一件闲置物品在毕业季之外也能高效流转，让每一位学生用更低成本获得所需教材与生活用品。

### 1.3 核心差异化

| 维度 | 传统二手平台（闲鱼/转转） | 本平台 |
|------|---------------------------|--------|
| 用户群体 | 全量社会用户 | 仅限高校在校生（学号认证） |
| 信任基础 | 芝麻信用/平台担保 | 同校身份+学号认证，交易风险可控 |
| 交易场景 | 快递物流为主 | 校内自提/宿舍配送，零物流成本 |
| 核心能力 | 通用搜索+推荐 | **书单批量匹配**：一次性找到拥有最多目标教材的卖家 |
| 商品结构 | 全品类泛供给 | 教材书籍为核心供给，数码/生活/文体为辅 |

## 二、目标用户

### 2.1 用户画像

| 用户类型 | 占比预估 | 核心特征 | 核心需求 |
|----------|----------|----------|----------|
| 教材采购型（买家） | 45% | 大一/大二学生，每学期需购买5-10本教材 | 低价获取教材、一次性买齐、减少跑腿 |
| 毕业清仓型（卖家） | 25% | 大四毕业生，大量教材/生活用品需处理 | 快速出清、批量处理、减少搬运 |
| 闲置流转型（买卖双向） | 20% | 大二/大三学生，数码/生活/文体物品交易 | 出售不用物品、淘高性价比二手 |
| 考研考公型（买家） | 10% | 大三/大四备考学生，需大量备考资料 | 低价获取备考书籍、资料匹配 |

### 2.2 用户痛点

**买家侧痛点：**
1. 新书价格高：大学教材均价40-80元，一学期教材花费可达300-500元
2. 买书跑腿多：不同课程教材分散在不同卖家手中，需多次联系、多次取货
3. 平台信任低：通用二手平台卖家身份不明，存在假货、欺诈风险
4. 物流成本高：快递费占二手书价格比例高，失去价格优势

**卖家侧痛点：**
1. 毕业清仓急：毕业季时间窗口短，大量物品来不及处理最终被丢弃
2. 单本出售慢：教材逐本发布、逐本沟通，时间成本高
3. 搬运成本高：物品需搬到快递点或约定地点，体力成本高
4. 平台抽成高：通用二手平台交易抽成+运费，实际收益低

## 三、核心价值主张

### 3.1 对买家

> **「输入一份书单，找到最全卖家，少跑几趟」**
>
> 通过书单批量匹配算法，将买家的多本教材需求与卖家的在售书籍进行多维匹配，按匹配数量排序，帮助买家一次性联系到拥有最多目标书籍的卖家，将"跑5个卖家买5本书"压缩为"跑1个卖家买5本书"。

### 3.2 对卖家

> **「一次发布，批量出清」**
>
> 卖家可批量发布教材书籍，通过书单匹配被动获得精准买家咨询，无需逐本推广；校内自提/宿舍配送模式消除物流成本，提升实际收益。

#### 4.2.5 二手书专区 — 书单匹配Tab（核心亮点）

**功能背景：** 学生每学期需购买5-10本教材，传统方式需在平台上逐本搜索、逐个联系卖家、多次取货，时间成本高。书单匹配通过算法将买家的多本需求与卖家的多本供给进行批量匹配，一次性找到最优卖家组合。

**用户价值：** 将"搜索N次→联系N个卖家→取货N次"压缩为"输入1次书单→联系1-2个卖家→取货1-2次"，预计节省70%以上的采购时间成本。

**交互流程：**
1. 用户在多行文本框中逐行输入书名（或直接粘贴整份书单）
2. 点击「开始匹配」
3. 系统按卖家维度统计匹配成功的书籍数量
4. 结果按「匹配本数」从高到低排序，匹配数相同则按「匹配总价」从低到高排序
5. 展示卖家卡片：卖家昵称、匹配本数/总需求数（如"5/5本"）、匹配总价、所在校区、交易方式
6. 点击卖家卡片展开：具体匹配的书目清单、单本价格、书籍成色
7. 点击「联系卖家」跳转私信页

**核心匹配规则：**
- 读取用户输入的多行书单，按换行符拆分为多个书名关键词
- 遍历所有在售二手书，按卖家维度统计匹配成功的书籍数量
- 匹配规则：**书名包含关键词即算匹配，不区分大小写**（V1.0采用包含匹配，预留后续升级为精确匹配+语义匹配）
- 同一卖家的同一本书只匹配一个关键词，避免重复计数
- 结果排序：匹配数量降序 → 匹配总价升序

**辅助功能：**
- 「清空」按钮：一键清空书单输入
- 「保存书单」按钮：将当前书单保存至「我的书单」，下次可直接使用
- 已保存书单列表：展示所有保存的书单，支持「使用」和「删除」

## 五、核心业务流程

### 5.1 核心交易闭环流程

```
买家路径：浏览/搜索 → 查看详情 → 联系卖家 → 线下沟通 → 校内交易 → 完成
卖家路径：发布闲置 → 等待咨询 → 私信沟通 → 线下交易 → 完成
```

### 5.2 书单匹配核心流程

```
输入书单（多行书名）
    ↓
按换行拆分关键词
    ↓
遍历所有在售二手书
    ↓
按卖家维度统计匹配数（书名包含关键词即匹配）
    ↓
排序：匹配数降序 → 总价升序
    ↓
展示卖家匹配卡片
    ↓
展开查看匹配书目清单
    ↓
联系卖家 → 线下交易
```

### 5.3 发布流程

```
选择发布类型（二手书/普通闲置）
    ↓
填写表单（必填项校验）
    ↓
上传图片（可选）
    ↓
点击确认发布
    ↓
前端校验通过 → 写入数据 → Toast提示 → 跳转我的上架
    ↓
校验失败 → 友好提示（如"请输入书名"）
```

## 六、核心逻辑规则

### 6.1 搜索逻辑

| 搜索场景 | 匹配字段 | 匹配方式 |
|----------|----------|----------|
| 全平台搜索（首页） | 商品标题、商品描述 | 模糊匹配（包含），不区分大小写 |
| 二手书专区搜索 | 书名、作者、ISBN | 优先匹配书名，其次作者、ISBN |

### 6.2 筛选逻辑

- 校区筛选：单选，商品校区完全匹配
- 交易方式筛选：多选，商品需同时包含所有选中的交易方式（AND逻辑）
- 价格筛选：区间匹配（min ≤ price ≤ max）
- 成色筛选：完全匹配
- 筛选条件实时生效，列表即时刷新（无需点击确认按钮）

### 6.3 书单匹配逻辑

详见 4.2.5 节核心匹配规则。

### 6.4 用户身份逻辑

- 首次使用：默认创建用户（昵称"我"，校区"北区"，未认证）
- 身份认证：手动填写学号+姓名+校区，提交后标记为已认证（V1.0不做真实校验）
- 认证标识：已认证用户在卖家信息区、私信会话、书单匹配结果中显示「已认证」徽章

### 6.5 数据持久化逻辑

- 所有数据（用户、商品、书籍、书单、消息、收藏）存储在浏览器localStorage中
- 首次打开页面时自动初始化Mock数据（6个用户、8件普通商品、20本二手书、4条消息）
- 数据初始化标记存储在localStorage中，避免重复初始化
- 刷新页面数据不丢失，清除浏览器数据则恢复初始状态

## 七、异常场景处理

| 异常场景 | 处理方式 | 用户提示 |
|----------|----------|----------|
| 搜索无结果 | 展示空状态页面 | "没有找到相关商品，换个关键词试试" |
| 分类下无商品 | 展示空状态 | "该分类下暂无商品" |
| 书单匹配无结果 | 展示空状态 | "没有找到匹配的卖家，试试调整书单关键词" |
| 发布时必填项为空 | 阻止提交，Toast提示 | "请输入书名"/"请输入有效的售价" |
| 图片上传超过上限 | 阻止添加，Toast提示 | "最多上传N张图片" |
| 收藏列表为空 | 展示空状态 | "还没有收藏任何商品" |
| 私信会话为空 | 展示空状态 | "暂无私信，去联系卖家吧" |
| 我的上架为空 | 展示空状态 | "还没有发布任何商品，去发布一件吧" |
| 商品/书籍不存在 | 展示空状态 | "商品不存在"/"书籍不存在" |
| 发送空消息 | 发送按钮禁用状态（输入为空时） | 无（按钮置灰不可点） |

## 八、V1.0 版本边界与后续规划

### 8.1 V1.0 不做的功能（明确裁剪）

| 功能 | 裁剪原因 | 后续规划版本 |
|------|----------|-------------|
| 在线支付 | MVP阶段验证信息匹配需求即可，支付涉及资质与合规，暂不接入 | V2.0 |
| 实时通讯（WebSocket） | 留言式聊天可满足MVP需求，降低开发复杂度 | V1.5 |
| 图书API/OCR识别 | 需第三方接口，MVP用手动填写替代 | V1.5 |
| 精确地理位置/地图 | 校内交易场景下校区标签足够，地图成本高 | V2.0 |
| 评价系统 | MVP阶段交易闭环简单，评价需积累足够交易数据 | V1.5 |
| 举报/风控系统 | 同校身份认证降低风险，MVP阶段人工处理 | V1.5 |
| 消息推送 | 无实时通讯则无需推送 | V1.5 |
| 后端服务 | MVP用前端+localStorage验证需求，预留API接口 | V2.0 |

### 8.2 技术架构预留

- 数据层（data.js）所有CRUD函数均为独立封装，后续对接后端API时只需替换函数内部实现，不影响上层逻辑
- 路由采用hash路由，后续迁移至后端路由或前端框架（React/Vue）成本低
- 书籍表继承商品表结构，额外字段（作者/ISBN/出版社/版次）独立存储，符合数据库设计范式
